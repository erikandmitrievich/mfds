* Problem 62 :binary_search_tree:lower_bound:sorting:
** Task
#+begin_quote
Argue that since sorting $n$ elements takes $\Omega(n \lg n)$ time in the worst case in the comparison model, any comparison-based algorithm for constructing a binary search tree from an arbitrary list of $n$ elements takes $\Omega(n \lg n)$ time in the worst case.
#+end_quote

** Solution

*Claim.* Every comparison-based algorithm that constructs a BST from an arbitrary $n$-element list has worst-case running time $\Omega(n \lg n)$.

*Given.*
- G1 :: Every comparison-based sorting algorithm has worst-case running time $\Omega(n \lg n)$. (Decision-tree lower bound.)

*Lemma* (in-order walk is free in the comparison model). =INORDER-TREE-WALK= on an $n$-node BST outputs its keys in sorted order, performs *0 key comparisons*, and runs in $O(n)$.

#+begin_quote
/Proof./ Its only branch is the test $x \neq \text{NIL}$ — a nil check, not a key comparison. Each node is visited once $\Rightarrow O(n)$. Sorted output follows from the BST property alone, i.e. from tree structure, not from any comparison performed at walk time. $\qquad\blacksquare$
#+end_quote

*Proof of Claim.*

1. Let $A$ be an arbitrary comparison-based BST builder; let $T(n)$ be its worst-case running time. /(Hypothesis: $A$ is unspecified, so the conclusion will hold for all such $A$.)/

2. Define $S :=$ "run $A$ on the input list; then run =INORDER-TREE-WALK= on the tree $A$ returns."

3. $S$ maps an arbitrary $n$-element list to that same list in sorted order. /(Lemma: the walk emits sorted keys.)/ $\Rightarrow S$ is a sorting algorithm.

4. $S$ is comparison-based: $A$ is, by (1); the walk contributes no key comparisons, by the Lemma. $\Rightarrow$ every key comparison performed by $S$ is performed by $A$.

5. Worst-case time of $S = T(n) + O(n)$. /(A's worst case, then the walk; the Lemma bounds the walk by $O(n)$.)/

6. Apply G1 to $S$ — legitimate, since (3) + (4) establish that $S$ is a comparison sort:

   $$T(n) + O(n) = \Omega(n \lg n).$$

7. $O(n) = o(n \lg n)$, so the additive term cannot absorb the bound:

   $$T(n) = \Omega(n \lg n). \qquad\blacksquare$$

Lines 3 and 4 are the only non-mechanical steps: (3) makes $S$ a /sort/, so the theorem is applicable at all; (4) makes $S$ a /comparison/ sort, so the theorem applies /here/. Everything else is composition and arithmetic.

* Problem 63 :binary_search_tree:predecessor:pseudocode:
** Task
#+begin_quote
Write the TREE-PREDECESSOR procedure for a binary search tree.
#+end_quote

** Solution

#+begin_src julia :results output
using Test

mutable struct Node{T}
    data::T
    left::Union{Node{T}, Nothing}
    right::Union{Node{T}, Nothing}
    parent::Union{Node{T}, Nothing}
end

function Node(data::T, left::Union{Node{T}, Nothing}=nothing, right::Union{Node{T}, Nothing}=nothing) where T
    node = Node{T}(data, left, right, nothing)
    (left !== nothing) && (left.parent = node)
    (right !== nothing) && (right.parent = node)
    return node
end

mutable struct BinaryTree{T}
    root::Union{Node{T}, Nothing}
    BinaryTree{T}() where T = new(nothing)
end

function tree_maximum(n::Node)
    while n.right !== nothing
        n = n.right
    end
    return n
end

function tree_predecessor(n::Node)
    if n.left !== nothing
        return tree_maximum(n.left)
    end
    y = n.parent
    while y !== nothing && n === y.left
        n = y
        y = y.parent
    end
    return y
end

@testset "tree_predecessor" begin
    #      4
    #     / \
    #    2   5
    #   / \
    #  1   3
    n1 = Node(1)
    n3 = Node(3)
    n5 = Node(5)
    n2 = Node(2, n1, n3)
    n4 = Node(4, n2, n5)

    @test tree_predecessor(n5) === n4
    @test tree_predecessor(n4) === n3
    @test tree_predecessor(n3) === n2
    @test tree_predecessor(n2) === n1
    @test tree_predecessor(n1) === nothing
end

* Problem 64 :binary_search_tree:counterexample:
** Task
#+begin_quote
Professor Kilmer claims to have discovered a remarkable property of binary search trees. Suppose that the search for key $k$ in a binary search tree ends up at a leaf. Consider three sets: $A$, the keys to the left of the search path; $B$, the keys on the search path; and $C$, the keys to the right of the search path. Professor Kilmer claims that any three keys $a \in A$, $b \in B$, and $c \in C$ must satisfy $a \leq b \leq c$. Give a smallest possible counterexample to the professor's claim.
#+end_quote

** Solution

Search for key $k = 4.5$ in the following BST:

#+begin_example
    1
     \
      4
     / \
    2   5
         \
          6
#+end_example

- $B$ (Keys on path): $\{1, 4, 5\}$
- $A$ (Keys left of path): $\{2\}$
- $C$ (Keys right of path): $\{6\}$

The claim asserts $a \leq b \leq c$ for all $a \in A$, $b \in B$, and $c \in C$. Choosing $a = 2 \in A$, $b = 1 \in B$, and $c = 6 \in C$ yields $2 \not\leq 1 \leq 6$. By ensuring no set is $\emptyset$, this avoids any vacuous truth loopholes. Therefore, the claim is definitively false.

* Problem 65 :binary_search_tree:predecessor:successor:
** Task
#+begin_quote
Let $T$ be a binary search tree whose keys are distinct, let $x$ be a leaf node, and let $y$ be its parent. Show that $y.key$ is either the smallest key in $T$ larger than $x.key$ or the largest key in $T$ smaller than $x.key$.
#+end_quote

** Solution

$x$ is a child of $y$, so it is either the left or right child.

Assume, without loss of generality, that $\mathrm{left}(y) = x$.
By the BST property, $x.key < y.key$.

Suppose some $z$ has $x.key < z.key < y.key$.
- $z.key < y.key \Rightarrow z$ is in $y$'s left subtree.
- $z.key > x.key \Rightarrow z$ is in $x$'s right subtree.

But $x$ is a leaf, so it has no right subtree. Contradiction. Hence $y.key$ is the smallest key larger than $x.key$.

By symmetry, if $\mathrm{right}(y) = x$, an identical argument establishes that $y.key$ is the largest key smaller than $x.key$. $\qed$

* Problem 66 :binary_search_tree:deletion:
** Task
#+begin_quote
When TREE-DELETE calls TRANSPLANT, under what circumstances can the parameter $v$ of TRANSPLANT be NIL?
#+end_quote

** Solution

#+begin_example
signature: TRANSPLANT(T, u, v)

TREE-DELETE(T, z)
1   if z.left == NIL
2       TRANSPLANT(T, z, z.right)      // replace z by its right child
3   elseif z.right == NIL
4       TRANSPLANT(T, z, z.left)       // replace z by its left child
5   else y = TREE-MINIMUM(z.right)     // y is z's successor
6       if y != z.right                // is y farther down the tree?
7           TRANSPLANT(T, y, y.right)  // replace y by its right child
8           y.right = z.right          // z's right child becomes
9           y.right.p = y              //     y's right child
10      TRANSPLANT(T, z, y)            // replace z by its successor y
11      y.left = z.left                // and give z's left child to y,
12      y.left.p = y                   //     which had no left child
#+end_example

1. Line 2: =TRANSPLANT(T, z, z.right)=
   - Condition: Called when $z.left == NIL$.
   - Evaluation of $v$: If $z$ is a leaf node, $z.right$ is also =NIL=.
   - Result: $v$ *can* be =NIL=.

2. Line 4: =TRANSPLANT(T, z, z.left)=
   - Condition: Called when $z.left \neq NIL$ and $z.right == NIL$.
   - Evaluation of $v$: The prerequisite guarantees $z.left$ exists.
   - Result: $v$ *cannot* be =NIL=.

3. Line 7: =TRANSPLANT(T, y, y.right)=
   - Condition: Called when $z$ has two children, and successor $y \neq z.right$.
   - Evaluation of $v$: $y$ is guaranteed to have no left child, but may also lack a right child. If $y$ is a leaf, $y.right == NIL$.
   - Result: $v$ *can* be =NIL=.

4. Line 10: =TRANSPLANT(T, z, y)=
   - Condition: Called when replacing $z$ with its successor $y$.
   - Evaluation of $v$: $y$ is derived via =TREE-MINIMUM(z.right)=. Since $z.right \neq NIL$ in this branch, a valid successor $y$ always exists.
   - Result: $v$ *cannot* be =NIL=.

Conclusion:

The parameter $v$ is =NIL= under exactly two circumstances:
1. Node $z$ (the node being deleted) has *no children*.
2. Node $y$ (the successor of $z$) has *no right child*.

* Problem 67 :binary_search_tree:deletion:commutativity:
** Task
#+begin_quote
Is the operation of deletion "commutative" in the sense that deleting $x$ and then $y$ from a binary search tree leaves the same tree as deleting $y$ and then $x$? Argue why it is or give a counterexample.
#+end_quote

** Solution

No, the operation of deletion in a binary search tree is not commutative.

Consider a binary search tree $T$ with the following structure:
#+begin_example
    2
   / \
  1   4
     /
    3
#+end_example

- Case 1: Delete $1$, then $2$

  Deleting $1$ (a leaf) replaces it with =NIL=.
  Node $2$ now has only a right child ($4$). Deleting $2$ elevates $4$ to replace $2$.
  The resulting tree has root $4$ with a left child $3$.

- Case 2: Delete $2$, then $1$

  Node $2$ has two children. Its successor is $3$ (the minimum of its right subtree). Node $3$ replaces node $2$, with $1$ becoming its left child and $4$ becoming its right child.
  Deleting $1$ (a leaf) replaces it with =NIL=.
  The resulting tree has root $3$ with a right child $4$.

The final trees have different structures (root $4$ vs. root $3$). Therefore, deletion is not commutative. $\qed$

* Problem 68 :red_black_tree:black_height:
** Task
#+begin_quote
What is the largest possible number of internal nodes in a red-black tree with black-height $k$? What is the smallest possible number?
#+end_quote

** Solution

Let $T$ be a red-black tree with $\mathrm{bh}(\text{root}) = k$.

- Smallest

  Every path from the root to a leaf contains exactly $k$ black nodes. The shortest such tree has no red nodes, so every node is black and the tree is a complete binary tree of height $k$:

  $$n_{\min} = 2^k - 1.$$

- Largest

  A red node has only black children, so on any root-to-leaf path red and black nodes alternate at best — at most one red node between consecutive black nodes. With $k$ black nodes per path, this gives height at most $2k$. The largest tree is the complete binary tree of that height:

  $$n_{\max} = 2^{2k} - 1 = 4^k - 1.$$

Thus,

$$2^k - 1 \le n \le 4^k - 1.$$

* Problem 69 :red_black_tree:node_ratio:
** Task
#+begin_quote
Describe a red-black tree on $n$ keys that realizes the largest possible ratio of red internal nodes to black internal nodes. What is this ratio? What tree has the smallest possible ratio, and what is the ratio?
#+end_quote

** Solution

- Largest ratio

  To maximize red internal nodes, alternate the colors by level. The root is black; a red node cannot have a red child, so levels must go black, red, black, red, etc. Take a complete tree whose deepest internal level is red.

  With levels $0,1,\dots,2j-1$ (level $i$ has $2^i$ nodes), black levels are the even-indexed ones and red levels the odd-indexed ones:

  $$\text{black} = \sum_{m=0}^{j-1} 2^{2m},\qquad \text{red} = \sum_{m=0}^{j-1} 2^{2m+1} = 2\sum_{m=0}^{j-1} 2^{2m}.$$

  Each red level holds exactly twice the nodes of the black level above it, so the ratio is exactly

  $$\frac{\text{red}}{\text{black}} = 2.$$

  The largest possible ratio is $2:1$.

- Smallest ratio

  A tree with no red internal nodes — every node black — is a valid red-black tree when $n = 2^k - 1$. Its ratio is

  $$\frac{0}{n} = 0.$$

  The smallest possible ratio is $0$.

* Problem 70 :binary_search_tree:rotation:pseudocode:
** Task
#+begin_quote
Write pseudocode for RIGHT-ROTATE.
#+end_quote

** Solution

#+begin_src julia :results output
using Test

mutable struct Node{T}
    data::T
    left::Union{Node{T}, Nothing}
    right::Union{Node{T}, Nothing}
    parent::Union{Node{T}, Nothing}
end

function Node(data::T, left::Union{Node{T}, Nothing}=nothing,
              right::Union{Node{T}, Nothing}=nothing) where T
    node = Node{T}(data, left, right, nothing)
    (left  !== nothing) && (left.parent  = node)
    (right !== nothing) && (right.parent = node)
    return node
end

mutable struct BinaryTree{T}
    root::Union{Node{T}, Nothing}
    BinaryTree{T}() where T = new{T}(nothing)
end

function left_rotate(t::BinaryTree, n::Node)
    y = n.right                              # y is n's right child
    n.right = y.left                         # y's left subtree becomes n's right subtree
    (y.left !== nothing) && (y.left.parent = n)
    y.parent = n.parent                      # n's parent becomes y's parent
    if n.parent === nothing                  # n was the root
        t.root = y
    elseif n === n.parent.left               # n was a left child
        n.parent.left = y
    else                                     # n was a right child
        n.parent.right = y
    end
    y.left = n                               # n becomes y's left child
    n.parent = y
    return t
end

function right_rotate(t::BinaryTree, n::Node)
    y = n.left                               # y is n's left child
    n.left = y.right                         # y's right subtree becomes n's left subtree
    (y.right !== nothing) && (y.right.parent = n)
    y.parent = n.parent                      # n's parent becomes y's parent
    if n.parent === nothing                  # n was the root
        t.root = y
    elseif n === n.parent.right              # n was a right child
        n.parent.right = y
    else                                     # n was a left child
        n.parent.left = y
    end
    y.right = n                              # n becomes y's right child
    n.parent = y
    return t
end

@testset "right_rotate" begin
    #      4              2
    #     / \            / \
    #    2   5   -->    1   4
    #   / \                / \
    #  1   3              3   5
    n1 = Node(1)
    n3 = Node(3)
    n5 = Node(5)
    n2 = Node(2, n1, n3)
    n4 = Node(4, n2, n5)

    t = BinaryTree{Int}()
    t.root = n4

    right_rotate(t, n4)
    @test t.root === n2
    @test n2.parent === nothing
    @test n2.left === n1
    @test n2.right === n4
    @test n1.parent === n2
    @test n4.parent === n2
    @test n4.left === n3
    @test n4.right === n5
    @test n3.parent === n4
    @test n5.parent === n4
end

* Problem 72 :red_black_tree:insertion:
** Task
#+begin_quote
The newly inserted node in RB-INSERT is set to the color red, which causes the problems with properties 2 and 4 of the RB–tree. If we would set it to black neither property would be violated. So why do we not set the new node to black instead of red?
#+end_quote

** Solution

1. Every node is either red or black.
2. The root is black.
3. Every leaf (NIL) is black.
4. If a node is red, then both its children are black.
5. For each node, all simple paths from the node to descendant leaves contain the same number of black nodes.

Inserting a *black* node immediately and unavoidably violates Property 5. It increases the black-height of every path passing through the new node by 1, leaving all other paths unbalanced. Because black-height is a *global* structural property, repairing this imbalance is highly complex and cannot be done cheaply.

Conversely, inserting a *red* node preserves Property 5 perfectly. It only potentially violates Property 2 (if the tree is empty and it becomes the root) or Property 4 (if its parent is also red). Because these are *local* violations, =RB-INSERT-FIXUP= can efficiently repair them in $O(\lg n)$ time using localized recoloring and rotations.

In short: a red insertion creates occasional, cheap-to-fix local problems, whereas a black insertion guarantees an expensive-to-fix global problem.
